### Concurrency Check

**Framework + DB combo:** FastAPI (async) + PostgreSQL + SQLAlchemy 2.0 (async)

| Concern | Risk | Mitigation |
|---------|------|------------|
| Concurrent expense creation | Low (different rows) | Atomic transactions, idempotency keys |
| Concurrent expense edit | Medium (same row) | SELECT FOR UPDATE row-level lock |
| Concurrent settlement + expense | Medium | Transaction isolation SERIALIZABLE for settlements |
| Balance reads during writes | Low | Derived balances computed in same transaction |
| Session table contention | Low (~50 users) | Not an issue at this scale |

## Architecture Decisions

### D-ARCH-1: Database — PostgreSQL (Normalized)

**Choice:** Fully normalized schema with foreign keys and constraints.

**Evidence:** Financial data requires ACID transactions, referential integrity, and `SELECT FOR UPDATE` for concurrency [tech-stack-advisor]. Amount in integer cents avoids float rounding errors [D-REQ-7].

**Schema:**

```sql
-- All amounts in integer cents (paise for INR)
-- Invariant: expense_splits.sum(paid_amount) = expense_splits.sum(owed_amount) = expenses.amount

users (
    id              SERIAL PRIMARY KEY,
    email           VARCHAR(255) UNIQUE NOT NULL,
    name            VARCHAR(100) NOT NULL,
    password_hash   VARCHAR(255) NOT NULL,
    created_at      TIMESTAMPTZ DEFAULT NOW()
)

groups (
    id              SERIAL PRIMARY KEY,
    name            VARCHAR(100) NOT NULL,
    type            VARCHAR(20) DEFAULT 'other',  -- trip, home, couple, other
    created_by      INTEGER REFERENCES users(id),
    invite_token    VARCHAR(64) UNIQUE NOT NULL,
    created_at      TIMESTAMPTZ DEFAULT NOW()
)

group_members (
    id              SERIAL PRIMARY KEY,
    group_id        INTEGER REFERENCES groups(id),
    user_id         INTEGER REFERENCES users(id),
    joined_at       TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(group_id, user_id)
)

expenses (
    id              SERIAL PRIMARY KEY,
    group_id        INTEGER REFERENCES groups(id),
    description     VARCHAR(255) NOT NULL,
    amount          INTEGER NOT NULL CHECK (amount > 0),  -- cents/paise
    currency        VARCHAR(3) DEFAULT 'INR',
    split_type      VARCHAR(10) NOT NULL,  -- equal, exact, percent
    expense_type    VARCHAR(10) DEFAULT 'expense',  -- expense, settlement
    category        VARCHAR(50),
    paid_by         INTEGER REFERENCES users(id),
    created_by      INTEGER REFERENCES users(id),
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW(),
    deleted_at      TIMESTAMPTZ,  -- soft delete
    idempotency_key VARCHAR(64) UNIQUE
)

expense_splits (
    id              SERIAL PRIMARY KEY,
    expense_id      INTEGER REFERENCES expenses(id),
    user_id         INTEGER REFERENCES users(id),
    paid_amount     INTEGER NOT NULL DEFAULT 0,  -- cents
    owed_amount     INTEGER NOT NULL DEFAULT 0,  -- cents
    UNIQUE(expense_id, user_id)
)

-- DB-level constraint (enforced via trigger or application):
-- For each expense: SUM(paid_amount) = SUM(owed_amount) = expense.amount
```

**Indexes:**
- `expenses(group_id, deleted_at)` — group expense listing (filter deleted)
- `expense_splits(user_id)` — user balance computation
- `expense_splits(expense_id)` — expense detail view
- `expenses(idempotency_key)` — dedup check

### D-ARCH-2: Read/Write Pattern — Mixed, No Cache

**Choice:** Option C (Mixed/Balanced), no caching layer.

**Evidence:** ~50 users, most operations are balance reads + occasional expense writes. PostgreSQL handles this trivially without cache. Caching financial data risks stale reads, which violates D-REQ-8 (derived balances).

### D-ARCH-3: Consistency — Strong

**Choice:** Option A (Strong Consistency).

**Evidence:** Financial balances must never be stale [D-REQ-8]. Single PostgreSQL instance = strong consistency by default. No read replicas needed at this scale.

### D-ARCH-4: Auth — Session-Based (HTTP-only Cookies)

**Choice:** Option A (Session-Based Cookies) from security decisions.

**Evidence:** Server-rendered app, no SPA = sessions are natural fit. HTTP-only + Secure + SameSite cookies prevent XSS token theft. Instant revocation by deleting server-side session [tech-stack-advisor, D-REQ-5].

**Implementation:**
- `itsdangerous` signed cookies for session ID
- Session data stored in PostgreSQL `sessions` table
- CSRF protection via double-submit cookie pattern
- Password hashing: bcrypt via `passlib`

**OWASP alignment (A07):**
- Rate limit login: 5 attempts / minute per email
- Session expiry: 30 days (long-lived for convenience, ~50 trusted users)

### D-ARCH-5: Authorization — Owner + Group Membership

**Choice:** Option D (Owner-Based) + group membership check.

**Rules:**
- Users can only see/modify expenses in groups they belong to
- Only the expense creator (or group admin) can edit/delete expenses
- Users can only leave groups with zero balance
- Enforced server-side via middleware + query scoping

**OWASP alignment (A01):**
- Every route checks: is user authenticated? is user member of this group?
- IDOR prevention: never expose sequential IDs in URLs without ownership check

### D-ARCH-6: Input Validation — Pydantic

**Choice:** Option A (Schema Validation) via Pydantic models.

**Evidence:** FastAPI uses Pydantic natively. Single source of truth for request validation.

**OWASP alignment (A03, A04):**
- All user input validated via Pydantic before hitting service layer
- SQLAlchemy ORM prevents SQL injection (parameterized queries)
- Amount validation: must be positive integer, within reasonable bounds
- Split validation: sum(splits) must equal total amount

### D-ARCH-7: Secret Management — Environment Variables

**Choice:** Option A (.env file, git-ignored).

**Evidence:** Solo developer, single deployment. Fly.io `fly secrets set` for production. `.env.example` in repo with placeholder values.

**Secrets needed:**
- `DATABASE_URL` — PostgreSQL connection string
- `SECRET_KEY` — session signing key
- `CSRF_SECRET` — CSRF token signing

### D-ARCH-8: Security Monitoring — Application Logging

**Choice:** Option A (Application Logging Only) with structured JSON.

**Events logged:** auth attempts (success/fail), expense create/edit/delete, settlement recording, authorization failures.

### D-ARCH-9: Scale Stage — A (MVP)

**Choice:** Stage A (Prototype/MVP).

**Evidence:** ~50 users, single server, ~$4/mo on Fly.io [tech-stack-advisor].

**Failure modes:**

| Component | Failure Mode | Impact | Mitigation |
|-----------|-------------|--------|------------|
| Fly Machine | Process crash | App unavailable | Fly auto-restart |
| PostgreSQL | Connection refused | All ops fail | Fly managed Postgres auto-recovery |
| Disk | Full | Writes fail | Monitor disk usage, small dataset |

**Backups:** Fly.io managed Postgres includes daily automated backups.

### D-ARCH-10: Testing Strategy

**Pyramid:** 60% unit / 30% integration / 10% manual (no e2e automation for MVP).

**Frameworks:** pytest + httpx (TestClient) + factory_boy

| Level | What to Test | Framework |
|-------|-------------|-----------|
| Unit | Debt simplification algorithm, split calculations, rounding, validation | pytest |
| Unit | Balance derivation from expense_splits | pytest |
| Integration | Expense CRUD (atomic transactions, idempotency) | pytest + TestClient + real Postgres |
| Integration | Auth flows (register, login, session, CSRF) | pytest + TestClient |
| Integration | Concurrency (concurrent edits, SELECT FOR UPDATE) | pytest + asyncio |
| Manual | Full user journey via browser | Manual QA |

**Test data:** Factories via factory_boy. No production data.

**CI:** GitHub Actions — lint (ruff) + type check (mypy) + unit + integration. All must pass to merge.

### D-ARCH-11: Observability — Minimal

**Choice:** Structured JSON logging to stdout. Fly.io captures logs natively.

**Health check:** `GET /health` returns 200 + DB ping status.
