# Requirements: Rup-Split

> Generated by /requirements on 2026-06-08
> Mode: standard
> Scope: app
> User level: 2
> Project state: greenfield

## Problem Statement

Free, self-hosted Splitwise alternative for ~50 users. Track shared expenses across groups, split costs multiple ways, simplify debts, and settle up — with strong data consistency and no race conditions. No payment links.

## Core Requirement

**Accurate, consistent balances with zero race conditions.** Every expense operation must be atomic. Balances must always reflect the true state of all expenses. Debt simplification must never rewrite history.

## Boundaries

- **Excluded:** Payment links/integrations, receipt scanning, multi-currency (v1), mobile native apps
- **Constraints:** ~50 users max, cheapest hosting, Python backend, single-currency per group (INR default)

## User Stories

- As a user, I want to create an account and log in securely, so that my expenses are private.
- As a user, I want to create groups (e.g., "Trip to Goa", "Roommates"), so that I can track expenses by context.
- As a user, I want to add an expense and split it equally, by exact amounts, or by percentages, so that I can handle any splitting scenario.
- As a user, I want to edit or delete an expense, so that I can fix mistakes.
- As a user, I want to see my overall balance (who owes me, who I owe), so that I know where I stand.
- As a user, I want to see simplified debts (A owes B, B owes C -> A owes C), so that settlement requires fewer transactions.
- As a user, I want to record a settlement (mark a debt as paid), so that balances update correctly.
- As a user, I want to see an activity feed of all expenses and settlements in a group, so that I have full transparency.
- As a user, I want to invite friends to a group via a link, so that onboarding is easy.

## Data Model (Core Tables)

| Table | Key Columns | Notes |
|-------|------------|-------|
| users | id, email, name, password_hash, created_at | Bcrypt hashed passwords |
| groups | id, name, type, created_by, invite_token, created_at | invite_token for shareable links |
| group_members | id, group_id, user_id, joined_at | Many-to-many |
| expenses | id, group_id, description, amount (integer cents), paid_by, split_type, category, created_at, updated_at, deleted_at, idempotency_key | Amount in cents to avoid float errors. Soft delete. |
| expense_splits | id, expense_id, user_id, paid_amount (cents), owed_amount (cents) | Invariant: sum(paid) = sum(owed) = expense.amount |
| settlements | Uses expenses table with type='settlement' | Uniform write pattern, full auditability |
| sessions | id, user_id, data, expires_at | Server-side session store |

## Debt Simplification Algorithm

Greedy approach (O(V^2)):
1. Compute net balance per person: net = sum(paid) - sum(owed)
2. Separate into creditors (net > 0) and debtors (net < 0)
3. Match max creditor with max debtor, settle min(|credit|, |debt|)
4. Repeat until all nets are zero
5. This is a **read-time optimization only** — never rewrites expense history

## Concurrency Strategy

1. All expense writes wrapped in BEGIN ... COMMIT transactions
2. SELECT ... FOR UPDATE on expense row before edit/delete
3. Idempotency key per expense creation (prevents double-submit)
4. Balances are **derived** (computed from expense_splits), never stored separately
5. Constraint: sum(paid_amount) = sum(owed_amount) = expense.amount enforced at DB level

## Assumptions

- Single currency per group (INR default) — multi-currency is v2
- ~50 concurrent users — no need for caching layer, read replicas, or CDN
- Users access via mobile browser — no native app needed
- Email-based auth is sufficient (no OAuth/social login for v1)
